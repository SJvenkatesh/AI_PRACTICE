# Example I — Connecting evals to observability

**Reference notes** (the scoring calls need a Langfuse account + keys).

**Evals** (Topic 10) test a fixed set of known cases in a lab. **Observability**
scores *every real production run*. Connecting them means: run your eval metrics
(citation rate, faithfulness, …) against real traces and attach the scores back
to those traces — so you can filter production for actual failures, not just
lab cases.

```python
# After scoring a real trace, attach the results in Langfuse
langfuse.score(
    trace_id="a1b2c3d4-...",
    name="citation_rate",
    value=1.0,
    comment="All required source IDs present",
)
langfuse.score(
    trace_id="a1b2c3d4-...",
    name="faithfulness",
    value=0.95,
    comment="LLM-judge score",
)

# In the Langfuse UI: filter traces where citation_rate < 1.0
#   → jump straight to every production answer that dropped a citation
```

## Why this matters

- **Evals** answer "does it pass our test suite?" — bounded, offline, known inputs.
- **Observability scores** answer "how is it doing on live traffic *right now*?" —
  unbounded, online, real inputs.

Attaching eval scores to traces closes the loop: a regression shows up as a
cluster of low-scoring traces you can open, inspect span-by-span (Example 6),
and fix — then confirm the fix on the next eval run.

## Sampling (don't score everything)

Scoring every request costs money/latency, so sample deliberately:

```
100% of errors traced + scored
100% of 👎 user-feedback traces
100% of external-facing outputs (QBR, IOH emails)
 10% of normal successful requests   (keep observability cheap)
```

The rule: never sample away failures or anything customer-facing; sample only
the routine successes.
