# Example B — ReAct pattern (Think + Act)

ReAct (Reasoning + Acting) is an agent pattern where the LLM thinks, decides to use a tool, observes the result, and repeats until it has enough information to answer.

The key idea is that the model doesn't try to answer everything from its own knowledge. Instead, it reasons about what information it needs, retrieves that information through tools, and then reasons again based on the observations.

User Question
      │
      ▼
+-------------------+
| Think             |
| What do I need?   |
+-------------------+
      │
      ▼
+-------------------+
| Act               |
| Call a tool       |
+-------------------+
      │
      ▼
+-------------------+
| Observe           |
| Read tool result  |
+-------------------+
      │
      ▼
Need more info?
      │
 ┌────┴────┐
 │         │
Yes       No
 │         │
 ▼         ▼
Think    Final Answer

**ReAct = Reasoning + Acting** — the most common agent pattern. The LLM
interleaves *thoughts* (reasoning) and *actions* (tool calls) in a loop, using
each observation to decide the next thought. It's the agent loop from Example A,
made explicit as a Thought → Action → Observation trace.

## A worked trace

```
Thought: I need the activation KPI for last week.
Action:  get_kpi(metric_id="D-110", weeks=1)
Observation: {"value": 12000, "prior": 24000}

Thought: 50% drop — check ops notes for the cause.
Action:  rag_search(query="SDK activation pause regions")
Observation: "SDK rollout paused in 2 regions"

Thought: I have enough evidence to answer.
Action:  FINISH
Answer: Activation fell 50% WoW (D-110). Ops notes cite SDK pause in 2 regions.
```

## Why ReAct works

- **Grounded**: each claim traces back to an Observation from a tool, not the
  model's memory — so the agent cites `D-110` / `ops_w25` instead of guessing.
- **Adaptive**: the path isn't fixed. If the first observation had shown *no*
  drop, the next Thought would go somewhere else. Good for exploratory questions
  where you don't know the steps in advance (contrast with Planning, Example E,
  for complex tasks where you *can* lay out the steps upfront).
- **Debuggable**: the Thought/Action/Observation log is a readable audit trail.

## Modern form

You rarely hand-write the "Thought:/Action:" text format anymore — the model
emits structured **tool calls** and the SDK parses them. The *loop* is identical;
only the wire format changed. `3.function_calling_agent.py` shows the real thing,
printing each THINK / ACT / OBSERVE step so you can see the ReAct loop turn.
