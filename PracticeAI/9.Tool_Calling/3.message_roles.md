# Example C — Message roles in tool calling

Tool calling is just a structured conversation using four message **roles**. The
whole loop from Example B is these messages accumulating in order:

```
┌─────────────────────────────────────────────────────────┐
│ role: system     │ Rules and persona                     │
│ role: user       │ User question                         │
│ role: assistant  │ tool_calls: [get_kpi, rag_search]     │  ← model REQUESTS tools
│ role: tool       │ {"value": 12000, ...}                 │  ← YOUR result for call 1
│ role: tool       │ [{"text": "...", "source_id": ...}]   │  ← YOUR result for call 2
│ role: assistant  │ "D-110 fell 50%... (ops_w25)"         │  ← final answer
└─────────────────────────────────────────────────────────┘
```

## The rules that matter

1. **The assistant `tool_calls` message must be kept in history.** When the model
   requests tools, you append that exact assistant message *before* the tool
   results. Drop it and the API rejects the follow-up (results with no matching
   request).

2. **Every `tool` message needs a `tool_call_id`** matching the id from the
   assistant's request. That's how the model pairs a result to the call it made —
   essential when several tools were requested at once (Example H).

3. **One `tool` message per requested call.** Two `tool_calls` → two `tool`
   messages. Missing one leaves a dangling request.

4. **The loop ends when the assistant returns content with NO `tool_calls`** —
   that message is the final answer.

## How the LangChain names map

| Concept | OpenAI wire role | LangChain message class |
|---|---|---|
| Rules/persona | `system` | `SystemMessage` |
| User input | `user` | `HumanMessage` |
| Model's tool request | `assistant` + `tool_calls` | `AIMessage` (with `.tool_calls`) |
| Your tool result | `tool` | `ToolMessage(content=..., tool_call_id=...)` |
| Final answer | `assistant` | `AIMessage` (`.tool_calls` empty) |

In `2.tool_calling_loop.py` you can see exactly this: the `AIMessage` with
`.tool_calls` is appended, then one `ToolMessage` per call (each carrying
`tool_call_id=tc["id"]`), then the loop repeats until an `AIMessage` arrives
with no tool calls.

Real-life analogy

Imagine you're talking to an assistant.

You:

Why did sales drop?

Assistant:

Let me check the sales database and last week's meeting notes.

(This is the assistant's tool_calls message.)

The assistant then asks two coworkers:

Finance: "Give me the sales numbers."
Operations: "Give me the meeting notes."

Each coworker replies separately:

Finance returns the sales data.
Operations returns the meeting notes.

Finally, the assistant combines both and answers you.

If the coworkers walked in and handed over reports without the assistant ever asking for them, it would be confusing. That's why the assistant's tool request message must remain in the conversation history—it provides the context that makes the subsequent tool results meaningful.

The complete message history

After everything is finished, the conversation history looks like this:

Order	Role	Purpose
1	system	Rules/persona
2	user	User's question
3	assistant	Requests one or more tools (tool_calls)
4	tool	Result for tool call #1 (tool_call_id matches)
5	tool	Result for tool call #2 (tool_call_id matches)
6	assistant	Final answer (no tool_calls)
